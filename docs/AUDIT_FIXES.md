## Migration and existing history

The migration does not rewrite the four previous ones. It preflights existing values and chains and aborts atomically if there is any divergence. There is no automatic repair, deletion of entries, or disabling of triggers. `down` removes only the new rules.

The tests apply and revert the migration on already populated databases and compare the rows before/after. A disposable database reproduces the corruption using the old schema; the upgrade is refused, the history remains intact, and the migration is not recorded as executed. DDL and history validation acquire locks: the cost on a large database should be assessed when planning the upgrade.

Metrics are operational observations, without durable delivery: a crash between COMMIT and the callback can still cause an operation to go uncounted. The ledger and the outbox events remain the persistent records.

## Dependency patches

The [braces](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) and [sprintf-js](https://github.com/advisories/GHSA-hp3w-g68c-fv3c) advisories listed no fixed release as of the validation date. We kept the versions and left the alerts visible, with versioned patches in `patches/` declared in `patchedDependencies` in package.json/lockfile:

- `braces@3.0.3`: limits nesting in the parser and in the recursive walkers. Deep patterns below the character limit and ASTs passed in directly are refused with a controlled syntax error. Common patterns and ranges keep working.
- `sprintf-js@1.0.3`: limits the precision of `e`/`f` to 0–100 and of `g` to 1–100, avoiding the RangeError from the reproduced precision specifiers. Common formats keep their output. This dependency lives in the migration tooling, outside the APIs/workers image.

The Dockerfile copies the patches before `bun install --frozen-lockfile`, including in the production stage. The tests load the installed packages, not simulated copies. **`bun audit` still reports two warnings and exits 1**, since it checks upstream versions. No advisory suppression was used. Reassess and remove the patches once a compatible upstream update is available; they do not represent a full audit of these libraries.

## Shutdown past the deadline

The additional probe confirmed that the old consumer returned from `stop()` while keeping two messages invisible after the deadline. It now tracks the entire received batch, stops heartbeats, waits for extensions already sent, and releases unacknowledged messages with zero visibility. Work that finishes after losing ownership does not ACK or change visibility using the old receipt. A second loop cannot start on the same instance while the first is still finishing.

`consumer-shutdown.test.ts` uses real PostgreSQL and SQS and pauses the SQL before the commit. With the deadline set to 100 ms, it verifies release of the active message and of the next message in the group; waits for a heartbeat period to pass; starts another consumer; releases the old commit; and confirms deduplicated redelivery, no late ACK from the old consumer, and an exact final balance. The test exercises the expiration branch without waiting for the 20-second default. The release is best effort if the broker is unavailable; in that case, the visibility timeout remains the recovery mechanism.

## Independent review of the 2026-10-23 fixes

The reviewer read the complete [Jungle Gaming challenge](https://github.com/junglegaming/backend-challenge), then AGENTS.md and ARCHITECTURE.md, and checked the implementation and executable tests independently. The reviewed fixes are now in commit `4638c8f`; the changes described below are left uncommitted. No commit, push, dependency update or migration edit was performed by this review. PostgreSQL and LocalStack were real Docker services throughout. The initial `verify` passed 280 tests; passing the existing suite alone did not establish correctness.

### Additional defects reproduced and fixed

**IR-01 (P2): retirement could block every publisher behind one locked event.** In `src/infrastructure/persistence/mikroorm/messaging.repositories.ts`, `retireAbandoned()` used an unrestricted UPDATE before every claim. An exhausted row locked by another transaction made the publisher wait or hit `lock_timeout`, even when unrelated events were ready. The new test `a locked exhausted event does not block retirement or publication of unrelated events` first failed because publication rejected with the lock held. Retirement now selects a bounded batch with `FOR UPDATE SKIP LOCKED`, updates those rows and lets unrelated claims proceed. The test now publishes the other three events to real SQS while the lock is held, then retires the abandoned row after release without another publication attempt. The port and caller in `src/application/ports/persistence.ports.ts` and `src/application/use-cases/publish-outbox-batch.use-case.ts` pass the batch and attempt limits explicitly.

Making retirement bounded also required an independent attempt-budget predicate in `claimDue()`. The test `an exhausted backlog larger than a retirement batch is never claimed again` caught an intermediate implementation republishing the eighth exhausted event after retiring seven. It now proves all eight events become DEAD at three attempts, over two batches, with no send to SQS. `an operator can requeue DEAD events without decreasing their immutable attempt history` protects the documented manual recovery path: clearing the lease and restoring PENDING permits delivery at attempt four. These are additional checks of the IR-01 implementation, not claims of an extra defect in the original unbounded query.

**IR-02 (P2): a known successful publication could remain DEAD.** The same repository's `markPublished()` accepted only PENDING rows. When the final publication was slow, another publisher could retire its expired lease before the original worker confirmed success. The original worker reported four publications while all four rows remained DEAD, misleading operators into redriving already delivered events. The new test `a successful publication confirmed after retirement is recorded as PUBLISHED` first failed with DEAD instead of PUBLISHED. It sends to real SQS, pauses before confirmation, expires the lease and retires the rows with another publisher, then releases confirmation. Successful confirmation now accepts PENDING or DEAD, while already PUBLISHED rows remain immutable. The test passes with delivery and persisted state agreeing. No attempt counter is reset.

**IR-03 (P2): reconciliation still exposed exact financial values in logs.** `src/application/use-cases/reconcile-wallet.use-case.ts` logged the stored balance, reconstructed balance and difference for a divergent wallet. Sanitizing database exceptions did not close this separate logging path. `divergence logs identify the failed checks without exposing wallet balances` first failed because serialized pino output contained `76.69`, `76.68` and `0.01`. Logs now contain identifiers, entry count, versions, checks and the existing alert. Exact amounts remain in the reconciliation response. The test uses the real PostgreSQL reconciliation and pino serializer and passes; the existing divergence metric and no-auto-correction test remain intact.

ADR-009 and ADR-013 document the reasons for these changes. The SQL predicates, lock acquisition, state updates and confirmation conditions were reviewed line by line. No financial settlement rule, applied migration, append-only protection or integration/concurrency assertion was weakened.

### Remaining limitations and validation scope

- Authentication remains the explicitly permitted no-op extension point. The injected scoped-resolver test proves controller enforcement, not a deployed OIDC integration or complete wallet-level authorization policy.
- Reference TTL is checked when a worker completes an attempt. The existing documented case in which the same pending-reference row repeatedly kills the process before an outcome still has no independent retirement watchdog; a database outage also delays expiry handling. The new default-TTL test covers a functioning worker, not permanent process failure.
- Outbox delivery is at least once. Lease expiry can duplicate a slow publication; downstream consumers must deduplicate stable event ids. DEAD events are retained and require operator intervention if no successful confirmation arrives. LocalStack restart durability and strict cross-publisher wallet event ordering remain outside the implemented guarantees.
- No load benchmark, live deployment, nginx Compose smoke check, dependency security re-audit or real AWS account test was performed in this review. Earlier reports of those checks remain historical. The final verify and compiled-process e2e use disposable databases and unique queues without restarting the existing application services.
- Superusers can bypass triggers. Reconciliation deliberately tests detection of such corruption; it does not grant the runtime login those privileges or silently repair history.
